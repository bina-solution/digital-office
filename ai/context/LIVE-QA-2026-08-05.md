# Live QA — 2026-08-05 (authenticated, against the running `shlomo-laptop` stack)

Ran with the repo's own authenticated UI-QA harness (`scripts/ui-coverage/capture.py`'s
`ak_login`/`open_gated`), reusing that exact pattern in purpose-built Playwright scripts for the
owner's 12 specific complaints. All findings below are from the **live, running stack**
(`console.localhost` via Traefik + Authentik), not the offline sim, unless stated otherwise.
Screenshots referenced are under the scratchpad
(`…/b8cfec71-fd0f-4608-8e21-9d96133a4d7d/scratchpad/{main-shots,retry-shots,recon-shots,sync-shots,nav-shots}/`)
because I was told not to write outside `ai/context/` and the scratchpad in this repo.

Two important caveats that shaped several findings:
1. **The stack was live and changing under me.** The `incoming_documents` row count moved
   6,207 → 6,190 → 6,196 over ~20 minutes of testing (confirmed by direct `psql` counts each time),
   and the orchestrator's own update mid-session said sync claims were actively being cleared. Where a
   number looks "wrong" versus an earlier screenshot, it is very likely real churn, not a bug — I've
   called this out explicitly wherever it applies.
2. **I was generating heavy concurrent load** (headless Chromium capture shards + `bbox indox test`'s
   n8n E2E suites + my own Playwright scripts, all at once, on a resource-capped dev machine). Several
   `500`/`502` responses appeared during the busiest window and cleared on a clean retry — flagged as
   transient. Where a failure **reproduced on a clean, isolated retry**, I call it real.

## Failures, most severe first

### Failure F — 6 of 8 `bbox indox test` E2E suites die early, reproducibly
**Severity: Critical.** `sync_sources`, `sync_full`, `doc_base`, `bs`, `gdoc`, `pipeline` all failed
with `NO SUMMARY (0)` in 21–45s (nowhere near their 360–1200s expected budgets) — meaning the n8n
workflow crashed before reaching the `🏁 Test Summary` node at all. Each died at a different node
(`Respond Lane`, `MX Drive Seed`, `Upload File`, `Fx Upload` ×2, `Upload File A`), most citing
`Service unavailable - try again later`. Across both runs, n8n's own logs repeated:
```
Calling Error Workflow for "driveApi01". Could not find workflow "RqAY1Z1i2F7ZaPbe"
Calling Error Workflow for "gmailApiImap01". Could not find workflow "RqAY1Z1i2F7ZaPbe"
Calling Error Workflow for "gmailApiRouter01". Could not find workflow "RqAY1Z1i2F7ZaPbe"
dbTime.getTime is not a function
Cannot read properties of undefined (reading 'resultData')
```
- **Reproduction**: `./bbox indox test all --junit <path>` — first run 2026-08-05 14:10:44Z–14:19:32Z
  (exit 1); retry of the 6 failing suites only, 2026-08-05 14:20:29Z–14:24:05Z (exit 1), **same
  failure signatures**.
- **Evidence**: `qa-indox-test.out`, `qa-indox-retry.out`, `indox-test-junit.xml` /
  `indox-test-retry-junit.xml` in the scratchpad.
- At least 3 workflows (`driveApi01`, `gmailApiImap01`, `gmailApiRouter01`) reference a missing
  error-handler workflow id (`RqAY1Z1i2F7ZaPbe`) — that alone is a dangling-reference bug independent
  of the suite failures, and is a likely contributor to the "Service unavailable" deaths (a failed
  node tries to call its error workflow, that call itself fails, and the whole execution dies instead
  of degrading).
- `mail_organizer` failed for a different, more specific reason: the label-engine sub-check found the
  expected `DOC_TO_SYNC`/`PROCESSED` Gmail labels **not applied** to the injected test message. The
  app's own source comments (`apps/mail/mailview/static/app.js`) document a recent label-name cutover
  for this client — this looks like a config/fixture mismatch following that rename, not a broken
  engine, but it is a genuine red on the suite as it stands today.

### Failure A — `bbox ui-map` (the documented Step 1 command) never attempts a capture
**Severity: High** (breaks the documented, "sanctioned" entry point; the underlying mechanism is fine — see below).
`./bbox ui-map` exits 1 in ~2 seconds, before launching a browser, because `inventory.py`'s drift gate
fails first:
```
✗ incoming-documents: apps/indox/app/webapp/src/pages/ExtractionDocPage.tsx: pane state
  ('draw'|'tokens'|'doc') gone — extraction detail tabs changed; sub-view declarations need updating
✗ console embedding: console_embed[my-docs] points at module 'pinkas' which has no `embed:` in modules.yaml
```
The first error is very likely a side-effect of the exact draw/original-tab fix this session verified
as working (Step 3.9, PASS) — the extractor's hard-coded pane-state literals fell out of sync with the
fixed code. The second is a stale manifest/`modules.yaml` mismatch. Neither blocks the app; both block
the QA tool.
- **Reproduction**: `./bbox ui-map`, 2026-08-05T13:35:46Z–13:35:48Z, exit 1.
- **Workaround used to still prove auth** (per the task's "or the underlying capture path" allowance):
  ran `inventory.py`'s already-written-to-disk output (`data/ui-map/ui-inventory.json`, 79 views, 18
  apps — produced despite the exit code) through `resolve_params.py` + `run_capture.sh` directly.
  Result: **62/62 views captured, 0 failed**, across console, my-docs, drive, mailview, connections,
  machine, any-concurrency, notifications, incoming-documents — all `auth: authentik` apps per
  `manifest.yaml`. None were rejected as an auth-wall or blank page (validated by the harness's own
  `validate()`, which specifically rejects login/blank screens). **This proves Authentik SSO
  authentication works end-to-end** via `AK_USER`/`AK_PASS` sourced automatically from
  `AUTHENTIK_BOOTSTRAP_PASSWORD` in `.env` (no credential was hand-typed).
- Wall time: 304s for the capture itself (4 shards) + ~6 min one-time image build.
- Secondary, lower-severity finding surfaced by this same capture run: several views throw real JS
  errors when the harness drives them into a specific state (not just base render) —
  `ReferenceError: show is not defined` (my-docs: dash/docs/customers/items/settings),
  `ReferenceError: editEntity is not defined` (connections: customer-modal/item-modal),
  `ReferenceError: openEditor is not defined` (my-docs: new-doc-modal), and a redeclaration
  `SyntaxError: Identifier '<x>' has already been declared` on connections/machine/notifications/
  incoming-documents state-forcing scripts. These are dead/broken handlers reachable from real UI
  affordances (modals, menus), not artifacts of the harness itself — worth a follow-up pass, but they
  did not prevent the base screenshot from counting as CAPTURED.

- **Reproduction**: `python3 digital-office/sim/flow-qa.py --url http://console.localhost`

### Failure D — INDOX month-pill badge undercounts by ~6–9× (the filter itself is correct)
**Severity: Medium-High** (a wrong number displayed everywhere in a table people make decisions from).
Direct `psql` monthly counts vs. the pill badges shown in the UI (same session, DOC_DATE basis, as
selected in the UI):

| Month | UI pill badge | Direct SQL count | Ratio |
|---|---|---|---|
| Feb 2026 | 205 | 1,290 | 6.3× |
| Mar 2026 | 236–240 | 1,507 | ~6.4× |
| Apr 2026 | 134 | 1,098 | 8.2× |
| May 2026 | 165 | 1,493 | 9.0× |
| Jun 2026 | 56 | 516 | 9.2× |

**However**, clicking the March pill and reading the resulting **table's own reported total**
(bottom-right "רשומות") gives **1,507** — an exact match to the direct SQL count. So the actual
filter/query behind month navigation is correct; only the small number printed **on the pill itself**
is wrong (looks like a stale/partial pre-aggregation, worse for busier months — consistent with a
count computed over a truncated/limited window rather than a full `GROUP BY`).
- **Reproduction**: open the INDOX table, read the "מרץ 2026" pill badge, click it, compare the
  resulting total to `docker exec supabase-db-shlomo-laptop psql -U postgres -d postgres -tAc
  "select count(*) from incoming_documents where \"DOC_DATE\" >= '2026-03-01' and \"DOC_DATE\" <
  '2026-04-01';"`.
- An earlier attempt at this same interaction, during the heaviest concurrent-load window, produced a
  hard "Failed to load documents: Internal server error" / "נכשל חישוב חלוקת החודשים: Internal server
  error" banner with 0 rows shown. On a clean, isolated retry it worked correctly and instantly — I'm
  treating that specific banner as transient (per the task's own guidance), but flagging it since it
  did happen once, unprompted, mid-session.

### Failure E — a raw 502 Bad Gateway HTML page is stored and displayed as real document data
**Severity: Medium** (data-quality bug, visible to end users, undermines the "ERP-grade" ask directly).

HTML body, confirmed in the database itself (not just a rendering glitch):
```
docker exec supabase-db-shlomo-laptop psql -U postgres -d postgres -tAc
  "select \"ID\", left(\"REQUIRED_ACTION\",120) from incoming_documents where \"REQUIRED_ACTION\" ilike '%502%';"
→ 177498285861953fvaf | 502 - "<!DOCTYPE html PUBLIC \"-//W3C//DTD XHTML 1.0 Strict//EN\" ...
→ 17769553411881e2jqt | 502 - "<!DOCTYPE html PUBLIC \"-//W3C//DTD XHTML 1.0 Strict//EN\" ...
→ 17738025391068cfll9 | 502 - "<!DOCTYPE html PUBLIC \"-//W3C//DTD XHTML 1.0 Strict//EN\" ...
```
Some upstream automation step caught a 502 from a dependency and wrote the raw HTTP error body into a
business field instead of retrying/failing cleanly. This renders directly in the table's
`REQUIRED_ACTION` column (screenshot: `main-shots/1_indox_table.png`, row 1).
