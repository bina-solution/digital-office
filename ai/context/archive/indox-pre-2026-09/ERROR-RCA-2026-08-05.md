### GlitchTip Error Reporter — root cause, fix, and live verification

The HTTP Request node POSTs to a hardcoded GlitchTip project id: `/api/1/store/`. GlitchTip's store
endpoint validates that the `sentry_key` in `X-Sentry-Auth` belongs to the project id in the URL. I
queried GlitchTip's own DB (`glitchtip-postgres`, `projects_project` / `projects_projectkey`):

- The key baked into the workflow (`ba06c13f8350cf7e77b6d6246278f2d2`) **does** belong to a real,
  active project key — but that project is `id=11` ("n8n"), not `id=1` ("any-concurrency").
- `.generated/glitchtip.projects.yml` (generator comment: "DO NOT EDIT... reconciled from each app's
  `observability{}`") provisions GlitchTip projects **alphabetically**. With today's 13-app roster,
  "n8n" is the 11th name alphabetically → GlitchTip auto-assigns it id 11 on a fresh DB. The workflow's
  hardcoded `/api/1/store/` is a stale value from an earlier roster (when n8n was presumably project 1).
- **Verified empirically**, not just inferred: `POST /api/1/store/` with the real key → `401 Invalid
  DSN`; the identical request against `POST /api/11/store/` → `422 Unprocessable Entity` (auth passed,
  payload was just an empty test body). That is conclusive: the key is fine, the URL's project id was
  wrong.

**Fix applied** (file I own): `platform-base/n8n/workflows/glitchtipReporter01.json`, `HTTP Request`
node — `url` changed from `http://glitchtip:8000/api/1/store/` to `http://glitchtip:8000/api/11/store/`,
plus an in-file `notes` field recording the reasoning for the next person who touches it. **Pushed to
the live instance** via `n8n import:workflow` + `n8n publish:workflow` (no container restart — the
memory budget forbids it, and none was needed: this is a passive sub-workflow, not a trigger).

**Verified working on real traffic, not just my test POST**: every "GlitchTip Error Reporter" execution
since the fix (14:07 onward) has been `success` — 5/5 in the ~15 minutes I watched (execs 79700, 79783,
80379, 80719, 80984), replacing a 100% failure rate. Every real error firing elsewhere in the system
(and there are plenty — see below) is now actually reaching GlitchTip for the first time today.

**Caveat / residual risk (did not fix, flagging for visibility):** the project-id-in-URL design is
fragile by construction — if an app with a name alphabetically before "n8n" is ever added to the
roster, "n8n" shifts to project 12 and this breaks again the same way. A durable fix would resolve the
project id dynamically (e.g. GlitchTip project-lookup-by-slug at runtime, or have the reconciler emit
the id into an env var the workflow reads) rather than hardcoding a number. Out of scope for today's
fix; noting it so it doesn't get rediscovered the hard way in a few months.

### Error Handler — root cause, NOT fixed (needs a secret + external state I don't have)

The `Telegram` node's `sendMessage` call 404s. This is deliberately NOT `continueOnFail` (see the
node's own `notes`: *"a rejected alert is a FAILURE and must show as one"*), so the alert failure
correctly surfaces as the whole "Error Handler" execution going red — that part of the design is
working as intended; it's the send itself that's broken.

Evidence for the cause, not just the symptom:
- `execution_entity` for "Error Handler" has **zero** `success` rows in the entire retained history
  (52 rows, all `error`, oldest retained 06:00 today) — this has been broken for as long as we have
  data, not a fresh regression.
- `.env:299` → `TELEGRAM_BOT_TOKEN=your-telegram-bot-token-here` — a placeholder, not a real token.
- The credential is literally named `N8N TG LOGGER [env-managed]`, and the `[env-managed]` suffix
  convention in this repo means its value is synced from `.env` via `CREDENTIALS_OVERWRITE_DATA` on
  every n8n start (confirmed that env var is set on the live container). A malformed/placeholder bot
  token breaks the `/bot<token>/sendMessage` URL shape, which Telegram's edge answers with **404**
  (not 401) because the URL doesn't match any bot route at all — this matches the exact error text
  seen on every failure.
- This is a genuine, live restart hazard on top of being currently broken: **every n8n restart re-syncs
  the placeholder into the credential store**, so even if someone manually re-enters a working bot
  token via the n8n UI, the next restart silently reverts it back to the placeholder.

**Fix needed (not applied — not in a file I own, and requires a real secret):**
`.env:299` needs the actual Telegram bot token for the "N8N TG LOGGER" bot. Whoever owns that bot
should also confirm chat `-1002488442473` still has the bot as a member with post permission — a 404
is also consistent with the bot having been removed from the group/supergroup, so the token alone may
not be the whole fix. I did not touch `.env` (not my file, and it holds a real secret, not something
to guess or fabricate).

## Root cause per class

### 1. `drive api` 503 — REAL DEFECT, not orphaning, not a symptom, and getting worse

`apps/drive/adapters/google_sa.py` (around the `_SA_NO_CREATE` constant, ~line 108) **deliberately**
raises this 503 by design — the code comment says so explicitly: a Google-Drive service-account
connection structurally cannot create/upload files (no personal storage, no Shared Drive granted), so
the adapter raises an actionable Hebrew error instead of letting Google's opaque 403 leak through.
**The bug is not in this adapter — it's that something keeps asking it to upload anyway.**

The call chain: `apps/indox/blueprint/n8n/syncV3Deliver0001.json`, node `d:upload` (~line 326 for the
node, connection resolution at **lines 533 and 734**) resolves the upload's `connection_id` from
`$('Item In').first().json.list_ctx.drive_connection_id` (falling back to `drive_profile_id`). That
value traces back to `connection_id: "drive_google_service_account-ea660043"` on the failing calls —
i.e. **some sync-registry / delivery-config entry (the "mail-private" folder in every sample I pulled)
is configured to deliver through the service-account connection when it must use the local Drive engine
(admin profile) or a user OAuth connection instead**, per the adapter's own error message. I could not
find a `registry`-named table in Supabase to point at the exact config row (registry state appears to
live inside the n8n workflow's own logic/Redis rather than a dedicated DB table) — whoever owns
`syncV3Deliver0001.json` / the drive sync registry should grep for `drive_google_service_account-ea660043`
as the delivery connection and repoint it.

**Blast radius:** real — this is a hard failure of every document delivery attempt through that
connection, not just noise. It's also the single largest error class by volume and **the only one
trending up rather than down**: 98 errors in one 15-minute window, 143 in the next. At that rate it
will keep dominating every future error-pulse run until the registry entry is fixed. Not in a file I
own; I did not touch `syncV3Deliver0001.json`, `driveApi01.json`, or `google_sa.py`.

## Continuous monitoring — `scripts/ops/error-pulse.sh`

New script, read-only, cheap (a handful of `psql -c` one-liners + 3 short `wget` calls; no rebuilds, no
restarts, no writes to any table). Auto-detects container names via `docker ps` so it works unmodified
on the VPS (`*-bina-deployment`) as well as this laptop (`*-shlomo-laptop`). Each run prints:

1. **n8n restart/redeploy churn** — main container `StartedAt`, plus `workflow_history` "import" rows
   in the window, by workflow. This is the confound-check: read this FIRST before trusting any crash
   number below it.
2. **error/crash counts by workflow**, last N minutes (default 15).
3. **New error-class fingerprints** not seen in a previous run — `<workflow, first ErrorClass: message
   text>`, diffed against `scripts/ops/.error-pulse-state/seen-fingerprints.txt` (gitignored, created
   on first run). Pure orphan-crashes (no error text at all) correctly collapse to one
   `<workflow>|<empty>` fingerprint per workflow instead of drowning out real classes.
4. **Stuck `sync_ledger` claims** — rows `claimed_at` older than the timeout (default 10 min) with no
   `delivered_at`, grouped by source/instance, plus the all-time status totals.
5. **`/incomingDocuments/sync/{registry,inventory,items}` timings** vs the documented 40s console-proxy
   read-timeout budget (see `apps/indox/app/incoming_documents/api/__init__.py`, the "console proxy's
   40s read timeout" comments) — elapsed seconds and % of budget for each.

Usage: `bash scripts/ops/error-pulse.sh [minutes] [claim_timeout_minutes]` (defaults 15/10).
