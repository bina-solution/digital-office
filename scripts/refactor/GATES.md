# The gate registry — one number, one gate

A **gate** is a cheap, mechanical assertion of an invariant this platform has already been burned by.
Nearly every one traces to a specific silent failure: something that kept reporting healthy while
being wrong. That is the bar for adding one — not "this would be nice to check", but "this broke
once and nothing noticed".

Until this file existed the registry lived only in CI step names and script docstrings, and they had
drifted apart: **three numbers were each used twice**, so "G21 failed" named two different gates and
a failure could not be looked up. Resolved 2026-07-30 in favour of whichever script declared the
number in its own docstring, because the code is the thing that runs:

| Was | Now | Why |
|---|---|---|
| `theme-token-lint.py` ran as G21 | **G27** | `route-claim-lint.py` declares G21 in its docstring |
| `tenancy-lint.py` ran as G22 | **G28** | `profile-gate-lint.py` declares G22; tenancy had no number of its own |
| `apps/indox/scripts/gen-engine-manifest.py --check` ran as G23 | **G29** | `gallery-default-lint.py` declares G23 |

## The standing rule: one defect class, seven instances — add a CLASS, not another script

**2026-08-06 produced the same defect seven times in one day.** Recorded here, in the file anyone
adding a gate reads first, because the individual fixes are worth much less than the pattern:

| # | two things that must agree | what failed | caught by |
|---|---|---|---|
| 1 | caller's payload vs sub-workflow trigger schema | field silently dropped before the first node ran | G39 |
| 2 | GATES.md vs each script's own docstring | three numbers each used twice; "G21 failed" named two gates | *(this file)* |
| 3 | decide function's literals vs its switch's cases | `extract_invoice_google_ai` + 4 more silently dropped | G41 / G51 |
| 4 | `Select Base`'s stamped flags vs the decider's read flags | every document ran BOTH the consolidated step and the two it replaced, all day | *(fixed 2026-08-06)* |
| 5 | one writer's casing vs the column's canonical domain | 90 rows invisible to every literal consumer | G54 |
| 6 | worker pin (`wsl-10g`) named in one place, not the other | carried from an 8-core profile | *(fixed 2026-08-06)* |
| 7 | a node's credential vs the endpoint it calls | 9 nodes 401ing across a whole app surface | G55 |

These are not seven incidents. They are **one missing habit**, and the generalisation is:

> **Derive an equivalence class from the code, then assert every member agrees.**

G39, G41, G51, G54 and G55 are already instances of that single form. It is cheap to instantiate and
it catches the *next* occurrence rather than the last one.

**So: when you find instance #8, add a class to an existing gate of this shape — do not write another
bespoke script.** A bespoke fix closes one hole; a class closes the shape. Two design rules learned
the hard way while building G54/G55, both of which decide whether the gate survives contact with the
codebase:

1. **Pick the coarsest key that still names a real thing.** Too coarse and the gate is permanently
   red on legitimate variation, which teaches everyone to ignore it — strictly worse than no gate.
   (G55 needed two path segments; one lumped every n8n webhook together. Another lane narrowed G54's
   sibling from 14 legitimate findings to a real invariant for the same reason.)
2. **Skip what you cannot resolve statically; never guess.** An expression-built URL or value is a
   false negative by design. A gate with false positives gets allowlisted into uselessness.
3. **A gate is not verified until you have watched it FAIL on the real thing.** Write the gate, then
   re-introduce the exact defect it exists to catch, and confirm it goes red — then restore. A green
   gate proves nothing about what it can catch; it is equally consistent with "clean" and "blind".
   This is not hypothetical: G56 was written to stop a client's Drive folder id being hardcoded in a
   shipped blueprint, and on its first run it **passed** when that literal was pasted back in. Every
   surviving pattern was URL-shaped (`drive.google.com/file/d/…`) while the actual incident was a
   naked `"1YpapJ3vJDYo…"` inside a JS expression — the bare-id pattern had been dropped moving from
   the throwaway sweep script to the gate. It would have shipped as a gate that green-lit the leak it
   was written for. **The false-clean pattern this whole registry exists to catch reaches into the
   machinery built to catch it**, so the detector needs the same proof-by-failure everything else
   here does. Keep the failure test with the gate (G56 keeps it as a self-test case), or the next
   refactor silently removes the pattern again.

And when a gate is green, **state its scope** — see G54's SCOPE note. An unstated scope is how a
green becomes a false clean.

> **Claiming a number: do this FIRST, before writing a line of the gate or its writeup.** grep this table AND `ls scripts/refactor/*.py` before picking one. Instance
> #2 above is exactly this collision, and it recurred on 2026-08-06: G52/G53 were claimed by another
> lane while these two gates were being written, and they had to be renumbered to G54/G55 after the
> fact. The code is authoritative (see the resolution table at the top of this file).

## Checks whose evidence is an ABSENCE (2026-08-07)

One night produced six instances of a single family, and the family is worth more than any of the
individual fixes. **A check whose passing evidence is an absence cannot distinguish "looked and
found nothing" from "never looked."** Every instance below reported a clean result while testing
nothing, and every one of them sat behind a green.

| # | the check | why it could never fail | what it hid |
|---|---|---|---|
| 0 | `if (lb.synced) ops.push({op:'addLabels', …})` then `return {ops, has_ops: ops.length>0}` | `lb` is `label_keys`; the `gmail-bs` lane sets `projection.synced_label`, which this node never reads. `lb.synced` is `undefined`, the `if` is false, **zero ops are built and nothing throws** | the label was never applied — and three separate hypotheses about label *semantics* all looked plausible because a guard that produces no work is downstream-indistinguishable from work that was attempted and failed. `has_ops:false` sat unread in the return value the entire time |

| 7 | `labels_map` supplied as `{key: 'string'}` instead of `{key: {name: '…'}}` | `nm()` reads `L[k].name`; a string has no `.name`, so resolution returns null and the function falls through to the same throw as if no map had been supplied at all | **the identical error message as the no-map case.** Shipping it would have produced the same red, and the conclusion would have been "`labels_map` doesn't work" when the fault was one level of nesting. Two different causes behind one indistinguishable symptom |

Instances 1 and 4 are the same defect wearing different clothes — a predicate that cannot match
its own column's format — and #4 is the sharpest, because **the sweep written to hunt this family
was itself a member of it**, and reported its own blindness as a clean result. That settles a
design question: a one-off script is not a safe way to sweep for this. It shares its target's
failure mode. Encode it as a gate rule.

### The positive control is the cheap general defence

Before trusting a zero, prove the instrument can produce a non-zero. The label probe that finally
settled `gmail-bs` did this and it is why its zeros meant something:

    label:INDOX/sv3s_synced -> 0      label:sv3s_synced -> 1
    label:INDOX             -> 0      label:INBOX       -> 5   <- the control

Without the `INBOX` row, `-> 0` is indistinguishable from a broken probe — which is the whole
family, reproduced inside the instrument being used to diagnose it.

### Two mitigations, which are habits rather than rules

**1. Before calling something unverifiable, name the probe that would verify it and say why that
probe is unavailable.** Instance #6 was labelled "not query-verifiable; the run is its proof" and
shipped on a reading of a guard. One `POST /search` — available the entire time, contract sitting
in `apps/mail/mailapi/service.py` — would have falsified it before a node changed. *Unverifiable*
and *unverified* are different words and the first one is a claim that has to be earned.

**2. When one fix appears to close several failures, verify they share a CODE PATH before
treating them as one defect.** `gmail-bs` and `proc-gmail-bs` produced near-identical label
failures and were treated as one bug. They were not:

    syncV3Deliver0001 / "Label Req"   (gmail-bs)
      labelIds:[j.projection.synced_label]     -> calls nm()? NO   labels_map? NO
    syncV3Deliver0001 / "Synced Label Ops"  (proc-gmail-bs)
      labelIds:[nm(lb.synced)]                 -> guarded

GB's label was passed straight through, unguarded and working. The "fix" derived from PB's guard
therefore broke a path that had been fine, by making `addLabels` apply a label nothing matches.
**A matching error message is evidence of a shared SYMPTOM, which is exactly what a shared
assertion produces — not of a shared cause.**

### Instance 0 is the sharpest, and it generalises to a rule

It is the only one where the absence was of an **action** rather than a match, and the signal was
already being computed: `has_ops: false` was in the return value and nobody read it. So:

> **An ops-builder that can return an empty batch must say so loudly, or its caller must assert
> non-empty.** Producing zero operations is a legitimate outcome and an indistinguishable one;
> only the builder knows which it meant.

### The through-line, recorded verbatim

> *Four retractions, all falsified by evidence rather than argument — and three of the four came
> from reading a mechanism instead of testing it.*

That sentence covers the `INDOX/` label fix, the shared-code-path claim, and the `chaos` timing
hypothesis in one. It is also the argument for why probe-first is worth its cost: **every one of
those three was cheap to test and expensive to assume.** The `nm()` probe that finally settled the
label question ran under `node` in seconds, against source lifted verbatim from the live
blueprint, and needed no deployment at all — it was available from the first minute.

### Two lists that silently disagree — five instances in one night

The other half of this family. Recorded because the count is the argument:

| the two lists | what diverged |
|---|---|
| repo blueprint `active` vs live n8n `active` | every push silently re-armed 11 test workflows |
| `GATES.md` table vs the gate scripts' own docstrings | `G57` claimed by `profile-passthrough-lint.py` with no table row; 55 scripts against 57-odd numbers |
| `label_keys` vs `projection.synced_label` | two field names for one concept; the executing node read only one |

| `labels_map` supplied by a caller vs rebuilt in `Take X` | the caller's map is discarded before the guard ever sees it |

thing that executes**, and where that is impossible, make the two lists the same object.

## Tightening a contract: enumerate every caller MECHANICALLY, before you tighten it (2026-08-09)

> **When you make an interface stricter, the enumeration of its callers is part of the change — and
> it must be produced by a gate, not by a person with `grep`. A manual survey silently misses
> whatever its pattern misses, and reports the miss as "no callers found".**

This repo shipped the *same* guard twice, three days apart, with opposite outcomes. The difference
was not the guard. It was whether the caller list was mechanical.

| | **drive**, 2026-08-06 (G46) | **mail**, 2026-08-09 (G62) |
|---|---|---|
| the guard | `apps/drive/app.py::_explicit_connection_required` | `apps/mail/mailapi/service.py::_explicit_connection_required` |
| scope | narrower — **the `/api/*` UI plane is EXEMPT** ("the SSO session is the authentication and the binding is the identity"); the guard sits at the `_op()` automation choke point only | **wider — no UI exemption.** The owner considered drive's exemption and overruled it on 2026-08-07: *"no fallbacks or so-called selected connection at mail app level… even then it's two separate calls — one to get the selected connection, one to act — never act blindly."* A browser-triggered action refuses exactly like an n8n one |
| caller survey first? | **yes** — every n8n workflow *and* every Python caller, repo-wide, before the guard landed | **no** equivalent survey |
| call sites fixed ahead of the guard | ~44 | 0 |
| staged warn-then-refuse rollout? | deliberately **skipped, and the survey is the stated justification**: the list was known and closed, so a warn phase would only have delayed a refusal nobody was going to hit | skipped with no such justification available |
| result | landed clean | `apps/mail/mailview` had **12** canonical-op call sites carrying no id. Every one began returning 400; the client's whole mail page returned 500 |

**The wider guard got the weaker rollout.** That inversion is the finding: mail's scope was
deliberately broader than drive's — a decision recorded in `service.py`'s docstring and correct on
its merits — and broadening scope *adds* callers, so it needed *more* enumeration, not less.

### Why "mechanical" is load-bearing, not a style preference

Mail's enumeration was not merely absent. A gate existed to do it — **G62**,
`mail-connection-lint.py`, whose whole job is "find every caller of a mail canonical op that names
no connection". It ran, it self-tested, and it reported **zero Python call sites through the entire
outage**, because of three separate holes, all now closed:

1. **The glob.** `apps/*/app/**/*.py` requires a directory literally named `app`. Only
   `apps/indox` has one, so the pattern resolved to **47 of 209** first-party app `.py` files — one
   app out of fourteen — while reading like "every app". `apps/mail/mailview/app.py` was never
   opened. *A gate reporting zero because it is looking at an empty set prints the same sentence as
   a gate reporting zero over a clean tree.*
2. **The service exclusion.** `scan_python` skipped `apps/mail/` wholesale as "the service". The
   service is `apps/mail/mailapi/`; `mailview` and `mailboxd` are their own compose services and
   are **callers**. One prefix too short excluded the thing being watched for.
3. **Helper-blindness.** The scan could only recognise a literal
   `requests.get|post("<canonical path>")`. `mailview` reaches mailapi through one `gi()` proxy
   helper, so twelve real call sites existed in a shape the pattern could not represent. This is
   the normal shape for a Flask front end here; a scanner that only reads un-abstracted calls can
   only check the callers that happen not to have factored their HTTP out.

Fixed and **proven before/after against the real file, not a paraphrase**: the pre-fix
`mailview/app.py` (from `HEAD`) now yields **14** findings — 12 call sites, 1 helper-contract, 1
opaque-error — and the fixed one yields **0**. A gate that cannot demonstrate both halves of that
has demonstrated nothing.

`mail-connection-lint.py` now prints **what it scanned** on every run, pass or fail
(`scanned: 338 first-party Python file(s) across 3 root(s) + 87 n8n workflow(s)`), and its own

the *positive control* rule from the "Checks whose evidence is an ABSENCE" section applied to a
gate's own reach: before trusting a zero, prove the instrument can produce a non-zero.

only exists if every hop between it and the operator preserves it.** G62 now flags a mail proxy
helper whose `raise_for_status()` sits outside any `try` and that never reads `status_code` or the
response text. (Inside a `try` is fine — that is the shape that translates the error rather than
deleting it.)

## A counter may reason from containment; a delete may not (2026-08-07)

`syncV3SourcesTest01`'s proc lanes count their delivered documents with

    where "SOURCE_ID" = 'sv3s_pg_src'          -- a FOLDER id

but both processors write the drive FILE id to `SOURCE_ID` and put the folder in `SOURCE_LINK`
(`SyncProcBS000001/Register`: `SOURCE_ID = $('Start').first().json.id`). So the counter is 0 by
construction, its watch never goes ready, and every downstream field assertion then reads null out
of an empty row — reported as `d:1, docs:0` plus a cascade of null mismatches, on lanes whose
delivery was working the whole time. Verified live: the old predicate matched 0 rows, the rows were
there.

The fix for the COUNTERS is to match what the product actually writes,
`coalesce("SOURCE_LINK",'') like '%sv3s\_pg\_src'` — end-anchored, `_` escaped.

**The same re-key was deliberately NOT applied to that node's `Cleanup SQL`, which has the
identical bug and therefore also deletes 0 rows.** A leading-wildcard containment match against
the live client table is exactly what G58 rule F3 forbids, and for exactly this reason: a row
whose `SOURCE_LINK` *mentions* a fixture folder is not thereby a fixture row. "Mentions something
of ours" is not "is ours" — that distinction is what the 2026-08-06 incident cost 2,432 documents
to establish, and a cleanup is not a place to relearn it.

So the rule, which generalises past this one node:

> **A read may reason from containment. A write may not.** A counter, a watch predicate, a
> dashboard tile may all say "this row mentions something of mine" and be useful. A DELETE or an
> UPDATE must say "this row IS mine", and only an anchored match on a registered marker column
> proves that.

The corollary is uncomfortable and worth stating: when the only fixture trace is mid-string, the
cleanup **cannot be fixed at the query**. It has to be fixed upstream, by making the writer stamp a
marker a delete is allowed to trust. That is the open finding those proc lanes exposed — they write
into the client's table under the PRODUCTION `SYNC_NAME`s (`drive-gdoc`, `drive-bs`), with the only
fixture evidence buried in a `SOURCE_LINK` URL, so the suite's own cleanup sees 0 rows and
`apps/indox/hooks/fixture-sweep.py` cannot see them either. They accumulate every run. Registering
`SOURCE_LINK` as a marker column would "fix" it by dissolving F3, which is the wrong trade.

**CLOSED at the writer, 2026-08-07 — and the counters went back to equality.** The delivery contract
already carried an opaque `list_ctx` from the unit to the processor, so the suite declares
`fixture_marker` on it, `syncV3Deliver0001`'s `Drive Proc Payload` validates it to a bare token and
puts it on the proc `ctx`, and both processors write it to **`SOURCE_ID`** — a column that was
ALREADY on `marker_columns` and ALREADY registered for `sv3s_`. Nothing new was registered and no
predicate was widened: `fixture-sweep` finds the rows with the `"SOURCE_ID" like 'sv3s\_%'` it
already builds, and the suite's `Cleanup SQL` — which has said `"SOURCE_ID"='sv3s_pg_src'` all along
and matched 0 rows — became TRUE rather than being rewritten. Measured live: marker stamped on both
lanes (`proc-bs` PASS 9/9), the exact-match cleanup matched 2, deleted 2, left 0, and the 401 client
rows on those two pipes were untouched. `SYNC_NAME` is deliberately unchanged, so routing and the
suite's own `sn === 'drive-gdoc'` assertion still hold.

Production cannot reach that branch, and it is structural rather than conventional:
`syncV3Main0001`'s `Build Units` constructs a real pipe's `list_ctx` field by field
(`{folderId, pair, type_hint, connection_id, max_bytes}`) and never spreads the registry entry, so
no key an operator adds to `data/registry/sync_registry.json` can become `fixture_marker`. Proven by
running the committed jsCode under `Build Units`' verbatim construction *including a registry row
that tries to set it* — 9/9, marker `null` in every production shape (`tmp/b3_marker_selftest.py`).

With the writer fixed, `PG Row` / `PV Row` / `PG W1 Watch` / `PV W1 Watch` were re-keyed from the
`SOURCE_LINK` containment match back to `"SOURCE_ID" = 'sv3s_pg_src'` / `'sv3s_pv_src'`. That is not
tidying: the containment counter is actively wrong while the 12 rows the OLD writer stranded are
still in the table. Measured with no lane running — containment counts **12**, equality counts
**0** — and execution 351226 reported `docs:13` against an expected 1, then read its field
assertions off a previous run's row (`COMPANY_DOC_ID SI9346523 != SI9351226`). Equality makes the
lane immune to debris instead of merely clean once somebody deletes it, and it fails LOUDLY (watch
times out) rather than silently passing if the marker ever stops being stamped. Those 12 rows are

## A subset check reads like an equality check (2026-08-07)

`scripts/ci/gates.sh` opens by saying the gate list had already drifted across two files and that
this one is now THE list. Its `--verify-ci` asserted that every gate in `GATES` appears in
`ci-verify.yml` — and never asked the reverse. So a gate could run in CI and be absent from the
canonical list, and five were, including **G58 itself**: the fixture-cleanup gate written after the
incident that deleted 2,432 client documents was a named CI step and missing from `GATES`, which
meant every LOCAL "run every gate" path — `gates.sh`, `fresh-machine-check.sh`, `baseline.sh` —
silently skipped it while `--verify-ci` printed *"ci-verify.yml enumerates all 40 gates"* and
exited 0.

> **A one-directional subset check phrased as a drift check is the same defect it exists to catch.**
> If two lists must be equal, assert both inclusions; `A ⊆ B` reported as "the lists agree" is a
> green that cannot see half its own subject.

The reverse check is now in `--verify-ci`. It found `auth-lint` (G6), `sso-provider-lint` (G20),
`theme-token-lint` (G27), `stalled-pagination-lint` (G49) and `fixture-delete-scope-lint` (G58).
All five were **measured to PASS before being adopted** — adding a red gate to the canonical list
would turn `gates.sh` red for every lane rather than fixing anything, and "make it green by not
running it" is how the list drifted in the first place. Count went 40 → 45; the suite's 10 failures
are the pre-existing ones and none of the five is among them.

## A PATCH to `workflow_entity` deploys NOTHING on n8n 2.17 (2026-08-07)

n8n 2.x splits a workflow into a **draft** (`workflow_entity.nodes`) and an **active version**
(`workflow_entity.activeVersionId` → `workflow_history.nodes`). **An active workflow executes the
active version.** A `PATCH /rest/workflows/<id>` writes the draft only: it returns HTTP 200, `GET`
reads the new nodes back, `workflow_entity.nodes` holds them — and the running workflow goes on
executing the old code indefinitely. Observed for 20 minutes on the proc lanes, and it surfaced only
because two nodes disagreed inside one execution: `Item In`.list_ctx carried `fixture_marker` while
the downstream `Drive Proc Payload`.ctx had no such key, which can only mean the reader was stale.

> **This invalidates a verification method.** "I queried `workflow_entity.nodes` and the new code is
> there" is a statement about the DRAFT, not about what runs. So is `GET /rest/workflows/<id>`. The
> only honest structural check is against `workflow_history.nodes` via `activeVersionId` —
> `tmp/b3_marker_active_audit.py` compares repo vs active version over full node `parameters`.
> Behavioural evidence (a document actually changing) was never affected.

Publishing is `POST /rest/workflows/<id>/activate {versionId}` — which is also n8n's ARM verb, so it
must never be called on the 11 deliberately-disabled test workflows. `bbox n8n push` already does the
right thing (its activation step sets the active version), which is why the sanctioned deploy path is
`scratchpad/push-batch1.sh` and not a hand-rolled REST call.

Two consequences worth chasing separately, neither fixed here:

* `tmp/run_patched.py` claims `/rest/workflows/<id>/run` executes the `workflowData` in the request
  body ("no push window needed"). It does not: `runManually` does
  `workflowRepository.get({ id: workflowId })` and uses only the run-data keys
  (`startNodes` / `triggerToStartFrom` / `pinData`) out of the body. Measured — a submitted copy with
  `Config` rewritten to a single lane produced execution 351226 emitting the STORED `{"lane":"all"}`
  and ran all ten lanes. Anything "verified" through that tool measured the unpatched workflow.
* `scratchpad/halt-tests.sh` disabled the test workflows with `update workflow_entity set
  active=false` and then SELECTed the same column back — **a check that passes by construction**.
  n8n 2.17 does not read it. Two places in the installed code decide from the version pointer
  instead: `WorkflowRepository.getActiveIds()` is `where: { activeVersionId: Not(IsNull()) }`, and
  `LiveWebhooks.executeWebhook()` resolves `webhook_entity`, loads the workflow with
  `relations: { activeVersion: true }`, throws `NotFoundError` only when the ACTIVE VERSION is
  missing, and builds the Workflow with `active: workflowData.activeVersionId !== null`. The
  `active` column is never consulted on that path. **FIXED 2026-08-07** — the script now clears
  both columns for 13 ids (the 11 originals plus `indoxV2DecideTest01` and `ztestMailDiscovery01`)
  and verifies with n8n's own predicate, exiting non-zero if any listed workflow survives it. Two
  facts the audit turned up and that the old check could not have:

  - `tVzFMkz18pCsXRyw` ("INDOX Reset - Drive Sync") was the one workflow where the columns
    disagreed, and the reason is upstream: its blueprint still declared `"active": true`, so every
    push re-armed it and the halt script cleared only the flag n8n ignores. It is now on
    `tmp/b3_active.py`'s list and its blueprint carries the safe state, so **0 of 13 blueprints
    would be re-armed by a push**. It was never reachable — manual + `executeWorkflowTrigger` only,
    no `webhook_entity` row, never executed — but that was luck, not the script's doing.
  - A `webhook_entity` row can outlive a deactivation: `ztestMailDiscovery01` still holds
    `GET ztest/mail-discovery`. Such a row is **inert** while `activeVersionId` is NULL, because
    `executeWebhook` throws "Active version not found" before running anything — which is why the
    halt script reports stale registrations rather than deleting registrations it does not own.

  **The same defect on two NON-test workflows — the case that made it real, now closed.**
  `indoxDataGateway01` ("INDOX Data Gateway (single writer)") and `indoxIdentity01` ("INDOX Identity
  (single source)") were created by agent lanes, are not part of the architecture, and were rejected
  by the owner. They were moved to `data/_attic_agent_drafts/` and set `active=false` — the exact
  half-measure above. Measured 2026-08-07: both still carried an `activeVersionId`, and
  `indoxDataGateway01` still held a registered `POST indox-data-gateway`. So an agent-created
  endpoint into the client's system was **live and servable** while the workflow list, the sync
  board and `tmp/b3_active.py report` all showed it off. Zero executions, so nothing was called.

  Disarmed by `tmp/b3_disarm_agent_drafts.sh`, in the safe direction only: full `workflow_entity`,
  `webhook_entity` and published-`workflow_history` rows backed up to `data/_registry_backup/` with
  sha256 first, then `set "activeVersionId" = null` on exactly those two ids, then the registration
  removed — in that order, so there is no instant at which a path resolves to a workflow that could
  still run. `active` left as found; `POST /activate` never used, because it is the ARM verb.
  **Nulling the pointer is the load-bearing kill and a restart is not required**: `findCached` keeps
  a positive webhook-routing entry that a DB delete does NOT invalidate, but `executeWebhook`
  re-reads the workflow per request and throws "Active version not found" before any node runs, so a
  stale cache entry cannot execute anything. Instance-wide two-column drift is now **0**.

## A value that crosses two dimensions has SEVEN homes, not six (2026-08-06)

The status-vocabulary drift (G48's family) is usually stated as "a STATUS value lives in six places:
`_DASH_STATUS_GROUP`, `_FAILURE_MAP`, `DOCUMENT_STATUS_VALUES`, `documentStatusKind`, the live
`STATUS_LABEL`, and the sim's `STATUS_LABEL` — miss one and the value renders as an unknown failure."
That is true, and it was one short.

`GARBAGE` is **both a TYPE and a STATUS**: `BaseDocEx01`'s `Select Base` stamps `TYPE:'GARBAGE'` and
`STATUS:'GARBAGE'` on the same row. So it also needs an entry in **`TYPE_LABEL`** — a seventh place,
in a different dimension, which the six-place checklist cannot see because every entry on it is a
status map. It was missed for exactly that reason: the work looked where the rule said to look.

`TO_EXTRACT` and `MERGED` are status-only and genuinely have six homes. The rule is therefore:

> **Before adding a value, ask which COLUMNS can carry it. Each column contributes its own set of
> vocabularies. A value that crosses TYPE and STATUS has seven homes; one that crossed a third would
> have more.**

NOT YET A LINT, and the reason is worth recording rather than leaving as an implied gap. G54
(`value-domain-lint`) owns a canonical **TYPE** domain and **no STATUS domain at all** — so the
cross-dimension check has no second list to intersect, and today `TYPE ∩ STATUS` is provably empty
and every TYPE value already has a label. A gate written now would be green with zero signal, which
is the "state the scope of a green" problem in gate form. Giving G54 a STATUS domain is the
prerequisite, and is independently worth doing: STATUS is the column that has drifted three times in
one day, and it is the one G54 cannot currently check.

## Why G1 was deleted (2026-07-30)

`compose-equiv.py` asserted "the rendered config is byte-equivalent to `.refactor/golden.raw.yml`,
modulo declared moves" — the gate the whole platform-OS refactor was declared safe under. It ran in
**no lane** and its golden was stale, which is worse than no gate at all, because the invariant was
still asserted in prose in six documents. The choice was re-golden-and-wire, or delete-and-amend. It
was **deleted**, and every document that asserted the invariant was amended in the same change.
`compose-equiv.py`, `moves.json` and `.refactor/golden.raw.yml` are gone (recoverable via
`git log --diff-filter=D -- scripts/refactor/moves.json` — that file is the record of the 23 declared
moves, the two service renames and the 30 reviewed diffs).

The decision was made by regenerating, not by preference. Three findings, in order:

**1. The tree the golden describes no longer exists.** `moves.json` declared 23 relocations; **all 23
old paths are gone from git** (`production/`, `development/`, `traefik/` — 0 tracked files each). A
gate whose job is "rewrite old→new and demand equality" cannot police moves that can no longer be
made.

**2. The diff is real work, not drift.** Rendering the current tree
(`reconcile.py render && ./scripts/dc config`) and running the gate gives **413 undeclared
differences**, 42 golden vs 40 candidate services (gone: homepage, portainer, redisinsight, webmail,
whatsapp-hacohanim; added: chat, mailboxd, mailserver-init). Every one traces to deliberate later
work, none to an accidental relocation:

| count | what it is |
|---|---|
| 130 | traefik router renames (`anyc-https` → `any-concurrency-https`) + `authentik@docker` → `@file` — **G21** and R5 |
| 81 | environment values (`supabase-db-shlomo-laptop` → `supabase-db`, `WA_CONTAINER` → chat, …) |
| 63 | `labels.homepage.*` vanishing across every service — the homepage app was deleted |
| 45 | other (depends_on, entrypoint, volumes lists) |
| 34 | `/var/run/docker.sock` → `/run/bbox-docker.sock` — **G32** |
| 34 | `volumes[].bind.create_host_path` — a docker-compose CLI *output-shape* change |
| 12 | `build.context` host-absolute (golden) vs repo-relative (now) |
| 6 | healthcheck timings |

Only those 12 `build.context` lines touch what `moves.json` existed to police, and they are a host
artifact rather than a move violation.

**3. Re-goldening could not have wired it into CI anyway — the render is not reproducible.** Two
renders of the **same commit on the same host** differ by **326 lines across 50 keys**, because
`scripts/ci-env.sh` mints fresh random secrets every run and the render interpolates them
(`PG_PASSWORD`, `AUTHENTIK_SECRET_KEY`, `N8N_ENCRYPTION_KEY`, `JWT_SECRET`, `REDIS_URL`, …). The
compose project `name:` and every `build.context` are the absolute checkout path, so they differ per
clone too. CI generates a throwaway `.env` on every run, so **no committed golden can ever match it**.
`packaging/OPTIMISATION.md` reached the same conclusion from the other end (the compiler emitted CRLF
on Windows, so a Windows-built and a Linux-built artifact differ byte-for-byte from identical
source). `moves.json`'s own allowlist had already conceded the point: 16 of its 30 declared diffs
were host-adaptive `ulimits`/`PG_NOFILE`/`COMPOSE_PROFILES` values and per-deployment glitchtip
secrets, two of them carrying the excuse *"G1 is a local dev gate (not run in CI)"*. Making it a CI
gate meant scrubbing 50+ secret keys plus the project name plus every absolute path — untested
masking logic in front of the comparison, which is exactly how an allowlist becomes a blindfold.

**Byte-equivalence is the wrong shape for compiled output.** `.generated/compose.yml` is *compiled*
from 27 manifests by `platform/manager/reconcile.py`; its service set is whatever `platform.state.yaml`
enables, so it legitimately changes on every app add, remove, enable or disable. A snapshot that must
be regenerated on every such change is a file reviewers rubber-stamp, and a 118 KB diff is not
reviewable. **What the render needs is property assertions, and it has them**: G0 and G6 run against
the rendered config itself (`ci-verify.yml`, "render the platform config"); G15, G18, G21, G24, G26
and G30 assert properties over the manifests and app composes it is compiled from. Between them they
cover what G1 was actually protecting — host paths, auth bypass, router claims, image pinning,
healthchecks, external resources, state volumes, memory budget — without pretending the bytes are
fixed.

If a future change needs parity across a migration again (`packaging/native-plan.md` wants one for
the container→native move), build it as an assertion over the **effective router/middleware set**, not
over the rendered bytes. Take the next free gate number; do not reuse G1.
