# digital-assets (נכסים דיגיטליים) + social-list (רשתות חברתיות)

The business's whole digital front — everything it shows the world — organised once and pushed
everywhere. Two apps, one job each:

| app | owns | speaks to |
|---|---|---|
| `digital-assets` | the **slots** (identity / content / media), every **version** of every asset, the **active** choice, the **channels** the business appears on, the ledger of what was **delivered** where | `social` (social-list), `sites`, and the office's own products through `GET /api/brand` |
| `social-list` | the **accounts** on social networks (vault instances) and ONE abstract API over them, `social.v1` | each network — through the office **browser** (browser42, the default on every network) or its official **API** |

Neither holds a credential: accounts are instances in the credential plane (`connections`), exactly
like drive, mail, domains and computers.

## The model

```
blueprint ──creates──► slots ──hold──► versions ──one is──► ACTIVE ──plan──► per channel:
 (research)            identity.logo.square                              push     automated, read back
                       identity.description.short
                       content.app-store.listing                          manual   tracked, done by hand
                       media.launch-day.launch-film  (a "set")            live     products read /api/brand
                                                                          skip     + the reason
```

* **Slot** — a named, typed place for one asset, with constraints (sizes, lengths, formats), a brief,
  and **targets** (`{channel, field?}`): where it shows up, and which profile field it feeds.
* **Version** — an asset: uploaded, made by the office agent (עזריה), imported, or typed. Never lost.
* **Active** — the version that IS the business now. Changing it is the one act that propagates.
* **Channel** — a place the business appears. The owner's eight are always present (YouTube,
  GitHub, website, Facebook, Instagram, X, Discord, WhatsApp); blueprints add listings (Google
  Business Profile, Wolt, B144…) and print surfaces (signage, invoices).
* **Plan → publication** — for every target: what will happen and why, then one delivery row per
  channel, watched until it ends. `ok` means the network READ BACK the new value.
* A **more specific slot wins**: `identity.profile.x.bio` covers X's bio, so
  `identity.description.short` skips X while the specific one is set.

## The user stories, and how each one runs

1. **"Add a logo, make it the active one, and it changes on all my accounts, website and products."**
   Slot drawer → add version → *make active* → the plan (Facebook avatar, X avatar: automatic through
   the office browser · Google profile: manual, opt-in · products: live) → *publish*. Each
   network gets its own rendition (social-list cuts 400×400 for X, 1640×624 for a Facebook cover…;
   an SVG master is rendered to PNG). Verified end to end on the test network, read back.
2. **"Update the slug, the description, the name — same thing."** Same flow for text slots; a
   Hebrew and an English name are separate slots, and each channel says which language it speaks.
3. **"עזריה creates media → it shows up in the right gallery → posted by a click or by the agent."**
   `POST /api/media {slot, …}` (the agent's brief, AGENT.md, is loaded into every session when the
   app is enabled) → the unit's gallery → `POST /api/posts` or the *post* button → per channel:
   an office-browser post (or an API post where the account is connected by API).
4. **"Every text and image on the website is a slot, editable here."** The site marks them with
   `data-da="<slot key>"` (+ `-src`, `-href`, `-content`, `-alt`) — `site_kit.py` scans a page
   (mapped vs still hand-written), and applies the active values (`GET /api/bundle`) in a build
   step or through `sites`. Scanning the owner's live site today: 0 mapped, 112 to map.
5. **"Ready media blueprints — startup-tail, business-basic, basic-restaurant."** Applying one creates
   every slot; `startup-tail` dates its 59 media units from the launch day (D0).

## Implementation kinds (social-list)

| kind | when | what the owner does |
|---|---|---|
| `browser` | **the default, on every network** — Facebook, Instagram, X, YouTube, GitHub, Discord, WhatsApp Web — through browser42, the office's own browser | logs in ONCE in the office browser's live view; watches the first run of each write script |
| `api` | an alternative where the network has an API for the op (GitHub, Discord bot, Facebook Page, Instagram posts, X, YouTube, WhatsApp Cloud profile) | pastes a token once; verified before it is stored |

There is no "prepare and let the owner click" kind: an op without a browser script answers `no` with
the reason until its script is written. The terms of X, Discord and WhatsApp forbid automating their
sites — shown next to the network as information; the office acts at a person's pace, only on actions
the owner started.

A browser write whose script has not been watched once refuses with `needs_verification`; a login or
2FA screen stops everything with `needs_human_login`; nothing retries a challenge.
