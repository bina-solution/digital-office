2. NEW system (target)

0.1.6 keeps periodic sweeping (Schedule → Get wrapper → API → repo) and gains a native Kafka trigger for live changes. The Python API is the only writer to repos and the sole publisher of change events to Redpanda — so live updates from both the GSheet repo and the Supabase repo flow through the same per-repo topic.

3. Side-by-side mapping

ConcernOLDNEW
Live triggerGoogle Sheets polling trigger inside 0.1.6Native Kafka trigger on ${prefix}.<repo> consumed directly by 0.1.6
Sweep / catch-upSchedule trigger + GSheet read inside helpersKept. Schedule trigger → Get wrapper → POST /documents/query → repo
Batch upsert (data side)Batch Upsert workflow: GSheet read → Code-node diff → googleapis batchUpdate + appendPUT /incomingDocuments/repos/<r>/documents → DiffEngine → GSheetRepo or SupabaseRepo
Batch getGet Incoming Document: switch (single/all/complex/custom-filter) → googleapis values.getPOST /incomingDocuments/repos/<r>/documents/query → unified Query translated per-backend
Event source for the busN/APython API publishes after every successful write — same topic shape regardless of backend (GSheet repos and Supabase repos both feed the same per-repo topic)
Schema mgmtImplicit (sheet header is the schema)POST /repos/<r>/schema/ensure — no-op for GSheet, real DDL for Supabase
Repo creationManual: create the sheet + tab + header by hand in GooglePOST /repos = transactional create_repo(): registers config and provisions the underlying storage. GSheet → creates spreadsheet (if no ID given) + adds tab + writes header + shares with editors. Supabase → creates schema + table + columns + PK index + grants. Plus Kafka topic. Idempotent; rolls back on failure.
Backend choiceHard-coded to one Google SheetRepoConfig.backend ∈ {gsheet, supabase} per repo, in registry JSON
Observabilityn8n executions UISentry + Redpanda console + structured logs in apitools
ReplayNot possibleRe-consume from Kafka offset
Helpers (Settings/Figure*/Query*/Extractors)n8nUnchanged

4. Migration boundary — request sequences

Two paths now exist into 0.1.6: live (Kafka) and sweep (Schedule). Both go through the same Python API.

4a. Live update path

sequenceDiagram
    autonumber
    participant Caller as Any caller
(0.1.6 wrapper, backfill, etc.)
    participant Py as apitools
PUT /repos/<r>/documents
    participant Repo as GSheet repo / Supabase repo
    participant Kp as KafkaProducer
    participant Bus as Redpanda
${prefix}.<repo>
    participant N8N as 0.1.6 (Kafka Trigger)

    Caller->>Py: PUT rows[]
    Py->>Repo: write
    Repo-->>Py: ok
    Py->>Kp: publish change event(s)
    Kp->>Bus: append (key = ID)
    Bus-->>N8N: deliver event
    note over N8N: 0.1.6 processes the event
(may then call Get + Batch Upsert wrappers)

4b. Sweep path (kept)

sequenceDiagram
    autonumber
    participant S as Schedule Trigger
    participant N8N as 0.1.6
    participant Getw as Get wrapper
    participant Py as apitools
    participant Repo as GSheet / Supabase

    S->>N8N: tick
    N8N->>Getw: query (filter / all)
    Getw->>Py: POST /documents/query
    Py->>Repo: read
    Repo-->>Py: rows
    Py-->>Getw: rows
    Getw-->>N8N: rows
    note over N8N: process rows the same way
as the Kafka path
(then writes via Batch Upsert wrapper)
